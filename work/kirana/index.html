Kirana — inventory and ordering system

A grocery business was tracking stock in a paper book and taking orders over WhatsApp. I built them a system where every order is a record with a status, a timestamp and a customer attached to it — and I've kept it running on their server ever since.

The situation

The business ran on two systems that didn't talk to each other: a paper book for what was in stock, and WhatsApp for what customers wanted. Both worked, in the sense that the shop stayed open. Neither produced a record you could look anything up in.

The practical consequence was that nobody could answer questions that should be easy. What did this customer order last month. How much of this item did we actually move. Was that order fulfilled or is it still sitting in a chat thread above forty newer messages.

What I built

A web application the owner and staff use from a browser, replacing both the book and the order thread.

  • Stock records with adjustment history — quantities change through recorded adjustments rather than being overwritten, so there's a trail of what changed and when.
  • Order lifecycle — an order moves through explicit states rather than existing as a message someone has to remember to act on.
  • Customer records tied to orders — order history is attached to a customer instead of scattered across chat threads.
  • Role separation — the owner and counter staff see different things and can do different things.

How it's put together

A React single-page application talks to an Express API over REST. The API owns all access to MongoDB — the browser never touches the database directly. The whole thing runs on one AWS EC2 instance.

nginx sits in front as a reverse proxy: it serves the built React bundle as static files and forwards API requests to the Node process on its internal port, so only one port is exposed to the world. PM2 supervises the Node process — it restarts it if it crashes and brings it back up when the instance reboots, which is the difference between a demo and something a business can open on a Monday morning.

Decisions and trade-offs

A single EC2 instance rather than a managed platform

Render or Railway would have deployed this in an afternoon with TLS handled for me. I chose a plain Linux box because the client needed to own the thing outright, and because I wanted to be the person who understands the whole path from a browser request to a database read.

The cost: I own the boring parts too — certificate renewal, process supervision, and being the one who notices when it goes down. There's no platform dashboard to tell me.

Stock adjustments as records rather than editable quantities

The simpler design is a number on the product you increment and decrement. I made each change its own record instead, so the quantity is derived from history rather than stored as a fact someone can quietly overwrite.

The cost: more writes, and reads need more care. For a business that had just lost visibility into where stock went, the trail was worth more than the simplicity.

What I'd change

  • TLS and a real hostname. It's served over plain HTTP on a bare IP, which means a browser warning before anyone sees anything. A subdomain with a Let's Encrypt certificate on the nginx already in front of it is an afternoon's work and I should have done it at launch.
  • Instrument it. There's no logging of what actually gets used. I can describe what the system does but not what it does most, which is the question I'd want answered before building the next feature.
  • Automated backups. A single instance with a single database is a single point of failure.

Outcome

It's been running on the same instance since launch, and the paper stock book is no longer in use.
